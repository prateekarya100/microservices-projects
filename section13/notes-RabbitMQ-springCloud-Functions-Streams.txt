Avoid Temporal coupling in microservices
-----------------------------------------

Ques=> What is Synchronous VS Asynchronous communication between microservices, which one is better in which situations ?
	   - Synchronous is used when a microservice needs an immediate response back from a different microservice
	   - Asynchronous is used when we don't need any immediate response from other microservice, just create an event trigger and send response later once 	
	     completed.
   	     
   	     example : eBanking website has => CustomerService, AccountService, LoanService, CardService
   	     								   when a customer want to see their bank balance they click on view balance,
   	     								   CustomerService calling AccountService to get balance related details on immediate basis. 

	     example : Ecommerce website => Customer-Service , Order-Service, Delivery-Service ,Tracking-Service
	     								when customer done order from Order-Service, where Order-Service simply shows their order placed,
	     								but not need any Delivery,Tracking on immediate basis. order service only responsible to trigger an
	     								event that order is placed , that event is triggers to delivery-service to response back once it is 
	     								completed.here order-service not waited for complete response of delivery-service instead it raises
	     								just an event trigger to delivery-service & order-service enjoys their holidays.

WHAT IS TEMPORAL COUPLING ?
-----------------------------------------------------------------------------------------
when we have multiple microservices, like ServiceA, ServiceB, ServiceC, ServiceD.
And microservice A wants to communicate with serviceB , it sent request to serviceB
via RestAPI during this communication if ServiceB responding too lately in that
scenerio ServiceA waits until ServiceB did not responds this is called Temporal Coupling.
-----------------------------------------------------------------------------------------

Ques=> How can we avoid temporal coupling in a microservices architecture ?
Ans=>  Using Asynchronous communication

Ques=> How many types of approaches in synchronous communication.
Ans=>  Imperative Approach , Reactive Approach

	   1> Imperative Approach: 
	   	-  if serviceA wants to communicate to serviceB,there will be a thread assigned to that process and that thread is blocked continuously,
	   	   until it does not getting a response from the serviceB thats why it takes too many time to response, its a plain synchronous communication
	   	   approach.

	   2> Reactive Approach:
	    -  there won't be any Thread get blocked instead, if a serviceA wants to communicate to serviceB, a Thread assigned to take this process under
	       consideration for a specific time only then go back into the thread pool, and again inside the thread pool its ready to take next upcoming
	       request to that microservice. Once the response from MicroServiceB comes into the picture again that Thread assign to process and response to
	       'MicroServiceA'  


--------------------------------------------------------------------------------------------------------------------------------------------------------
														 EVENT DRIVEN BY Pub/Sub or BY Apache KAKFA
--------------------------------------------------------------------------------------------------------------------------------------------------------

Pub/Sub - In this model one service is published an event into message broker like RabbitMQ , that published event subscribed by other service to consume
		  information about or an event triggered.
		  It can not be re-played means users who joined later not able to access past events , once it is published it only available to those who subscribe that event else no other user can't able to see previous events happened.


Apache KAFKA - Events are written to a log in a sequential manner.
			   producer produced events and those events are stored in a well order fashion.	
			   Instead of subscribing events consumers have the ability to read any part of the event stream.
			   Events can be replayed, which allowing clients to join at any time and recieves all past events.

Ques=> RabbitMQ for Pub/Sub Communication why ?
	   - Uses AMQP (Advanced Messaging Queuing Protocol)
	   - Distributed deployment
	   - Monitoring of Messages
	   - Recent versions of Rabbit-MQ, now also capable to provide event streaming

	   PRODUCER - send messages (aka PUBLISHER)
	   CONSUMER - received messages (aka SUBSCRIBER)
	   MESSAGE BROKER - Middleware in between producer & consumer, messages sent by producer received at message broker and sent them to appropriate consumer.

	   AMQP - works on two principals:
	   							    - exchange -> sent message receive by producers and sent them to respective queues which consumers subscribed.
	   							    - queues   -> from the respective queues inside the message broker , whatever queue subscribed by the consumer at the
	   							    			  end of consumer side, they'll read the message from the respective queue and read the message.

	   							    *** NOTE *** 
	   							    		THERE CAN BE MULTIPLE EXCHANGES AVAILABLE, OR THERE CAN BE MULTIPLE QUEUES IT DEPENDS ON THE NO. OF EXCHANGES,QUEUES IN THE SYSTEM BY PRODUCER/CONSUMER.
	   							    		Any producer can produce many no. of exchanges, similarly. a consumer can subscribed many no. of queues at the time.
